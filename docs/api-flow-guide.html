1 Normal Trip Lifecycle (Happy Path)

This is the standard flow when no exceptions occur. Both mobile and dashboard use the same endpoints.

1
Create trip — Vehicle arrives at origin center
POST /trips   body: { vehicleId, originCenterId, purpose }
Phase: AT_ORIGIN_ARRIVED • Auto-adds vehicle to LOADING queue
↓
2
Start loading
POST /trips/:id/start-loading
Phase: AT_ORIGIN_LOADING • Starts queue service
↓
3
End loading
POST /trips/:id/end-loading
Phase: AT_ORIGIN_LOADING_ENDED
↓
4
Set destination & mark ready to exit
POST /trips/:id/set-destination   body: { destinationCenterId }
Phase: READY_TO_EXIT
↓
5
Exit origin — Vehicle leaves center
POST /trips/:id/exit-origin
Phase: IN_TRANSIT • vehicle.status = IN_TRANSIT
↓
5b
Set ETA NEW — Optional but recommended for overdue detection
POST /trips/:id/set-eta   body: { estimatedArrivalAt: "2026-04-17T15:30:00Z" }
↓
🚚
Vehicle is on the road. If anything goes wrong during transit, see Flows A-E below.
↓
6
Arrive at destination
POST /trips/:id/arrive-destination
Phase: AT_DESTINATION_ARRIVED • Auto-adds to UNLOADING queue
↓
7
Start unloading
POST /trips/:id/start-unloading
Phase: AT_DESTINATION_UNLOADING
↓
8
End unloading
POST /trips/:id/end-unloading
Phase: AT_DESTINATION_UNLOADING_ENDED • DELIVERY auto-completes to COMPLETED
↓
9
Complete trip (only needed for PICKUP purpose)
POST /trips/:id/complete
Phase: COMPLETED

EndpointPurpose

2 Flow A — Vehicle Breakdown

Driver calls dispatcher. Dispatcher opens the in-transit trip on dashboard or app.

🔧 Step 1 — Report breakdown (Mobile or Dashboard)

POST /exceptions/trips/:tripId/report

Body:

type"BREAKDOWN" (required)
location"N4 highway, km 142, after Edea junction" (required, free text)
description"Engine overheated. Coolant light on 20min." (required, free text)

Result: trip.phase → BREAKDOWN • exception.status = ACTIVE • Returns exception with ID

↓

Dispatcher chooses one of three resolution paths:

Option A — Send Technician

1. POST /exceptions/:exceptionId/dispatch-technician

technicianName"Jean-Paul Mbarga"
technicianPhone"+237 677 123 456"
estimatedArrivalTime"14:30"
notes"Coming from Douala workshop" (optional)

Result: trip.phase → AWAITING_REPAIR • exception.status = IN_PROGRESS

2. Add updates while waiting (optional, repeatable):
POST /exceptions/:exceptionId/notes   body: { note: "Technician on site now" }

3. POST /exceptions/:exceptionId/mark-repaired

repairedBy"Jean-Paul Mbarga"
repairDescription"Radiator hose replaced. Coolant refilled."
repairReference"REP-2026-042" (optional)

Result: trip.phase → IN_TRANSIT (resumed!) • exception.status = RESOLVED_RESUMED

Option B — Transfer Goods to Rescue Vehicle

See Flow C (Section 4) for the full transfer flow.

Option C — Return Goods to Origin

POST /exceptions/:exceptionId/return-to-origin

Body: { reason: "Cannot repair. No rescue vehicle available." }

Result: trip.phase → CLOSED_RETURNED • trip.status = COMPLETED • exception.status = CLOSED_RETURNED

3 Flow B — Road Accident

Driver calls dispatcher, or reports directly from the mobile app (3-step form).

🚨 Step 1 — Report accident (Mobile or Dashboard)

POST /exceptions/trips/:tripId/report

FieldValueRequired
type"ACCIDENT"Yes
location"N3 road, km 67, between Edea and Douala"Yes
description"Rear-ended by truck at roundabout"Yes
severity"MINOR" | "MAJOR" | "CRITICAL"Yes (accident)
hasInjuriesfalseNo
isCargoDamagedtrueNo
cargoDamageDescription"3 pallets shifted, outer packaging torn"No
isVehicleDriveablefalseNo
policeReportReference"PV-2026-04-001"No

Result: trip.phase → ACCIDENT • exception.incidentReference = "INC-20260417-001" (auto-generated)

↓

Same 3 resolution options as Breakdown: dispatch-technician / dispatch-rescue-vehicle / return-to-origin

📷
Photos: Uploaded separately via your file storage service. Photo URLs are stored in the exception_photos table. The GET /exceptions/:id endpoint returns the photos array.

4 Flow C — Goods Transfer to Rescue Vehicle

Triggered from a Breakdown or Accident exception when goods need to move to another vehicle.

🔄 Step 1 — Dispatcher selects rescue vehicle (Dashboard)

First, list available vehicles: GET /vehicles/by-status/AVAILABLE

Then dispatch: POST /exceptions/:exceptionId/dispatch-rescue-vehicle

rescueVehicleId17592 (required)
transferLocation"N4 km 142, breakdown site" (required)
estimatedArrival"15:00" (optional)
notes"Dispatched from Douala center" (optional)

Result: trip.phase → TRANSFER_IN_PROGRESS • exception.status = IN_PROGRESS

↓

Step 2 — Rescue vehicle arrives, staff scans QR (Mobile)

Mobile app scans rescue vehicle QR code:

GET /vehicles/qr-code/:qrCode → Confirms plate matches, shows original trip info

↓

Step 3 — Confirm transfer complete (Mobile)

POST /exceptions/:exceptionId/confirm-transfer

cargoCountTransferred12 (pre-filled from manifest, editable)
cargoCondition"GOOD" | "MINOR_DAMAGE" | "MAJOR_DAMAGE"
notes"All 12 pallets transferred. No visible damage." (optional)

What happens:

  • Original trip → CLOSED_TRANSFERRED (sealed, read-only)
  • Rescue trip → auto-created, phase = IN_TRANSIT, isRescueTrip = true, originalTripId = original trip ID
  • Original vehicle → status = AVAILABLE
  • Rescue vehicle → status = IN_TRANSIT

Response: { exception, rescueTrip }

↓

Step 4 — Rescue vehicle arrives at destination (Mobile — normal flow)

The rescue trip follows the standard arrival flow:

POST /trips/:rescueTripId/arrive-destination
POST /trips/:rescueTripId/start-unloading
POST /trips/:rescueTripId/end-unloading → Rescue trip COMPLETED

5 Flow D — Overdue / No-Show

Triggered by frontend timer (checks ETA) or manually by dispatcher.

⏱ Step 1 — Flag as overdue

POST /exceptions/trips/:tripId/report

type"OVERDUE"
location"Unknown - last known: departed from Douala"
description"Vehicle 45min past expected arrival time"

Result: trip.phase → OVERDUE • exception.status = ACTIVE

↓

Step 2 — Dispatcher investigates

Get driver phone: GET /trips/:id?include=vehicle

Log each call attempt (repeatable):

POST /exceptions/:exceptionId/log-call-attempt

outcome"ANSWERED" | "NO_ANSWER" | "VOICEMAIL"
notes"Driver says stuck in traffic. New ETA: 16:00" (optional)

If driver gives new ETA:
POST /trips/:tripId/set-eta   body: { estimatedArrivalAt: "2026-04-17T16:00:00Z" }

If driver reports breakdown/accident:
POST /exceptions/trips/:tripId/report with type: "BREAKDOWN" or "ACCIDENT" (opens Flow A or B)

↓

Step 3 — Escalate if unreachable (after 2h or dispatcher's discretion)

POST /exceptions/:exceptionId/escalate

reason"DRIVER_UNREACHABLE" | "SUSPECTED_BREAKDOWN" | "SUSPECTED_ACCIDENT" | "UNKNOWN"
contactAttemptsMade5
notes"Phone off since 14:00. Police notified." (required)
actionsTaken["REPORTED_TO_POLICE", "NOTIFIED_MANAGEMENT"] (optional)
policeReportReference"PV-2026-04-003" (optional)

Result: trip.phase → NO_SHOW_ESCALATED • trip.status = COMPLETED (sealed) • exception.status = ESCALATED

6 Flow E — Police Stop / Other

Simple flow. Logs the event, dispatcher is notified, trip stays IN_TRANSIT.

Report from mobile

POST /exceptions/trips/:tripId/report

type"POLICE_STOP" or "OTHER"
location"Checkpoint before Yaounde bypass"
description"Routine document check. Estimated 30min delay."

Result: trip.phase stays IN_TRANSIT (no phase change) • exception.status = ACTIVE • Dispatcher sees it in active exceptions list

9 Overdue Detection (Frontend Logic)

The backend provides the data. The frontend compares current time against the ETA.

⏱
No GPS. Overdue is purely time-based. The frontend polls GET /trips?status=ONGOING&phase=IN_TRANSIT and compares trip.estimatedArrivalAt against the current time.
ThresholdFrontend ActionAPI Call
ETA + 30 minShow amber "Overdue" badge on tripOptional: auto-report via POST /exceptions/trips/:id/report { type: "OVERDUE" }
ETA + 1 hourShow orange alert + "Call driver" prompt—
ETA + 2 hoursShow red alert + "Escalate" prompt—

The dispatcher can also manually flag any trip as overdue from the trip action menu at any time.
